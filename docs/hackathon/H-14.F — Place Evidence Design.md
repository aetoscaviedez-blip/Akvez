## 3. Arquitectura actual

```
Google Places  →  googlePlacesAdapter.ts:160-172   (servidor)
                        ↓  nombres ya neutralizados
                  DTO HTTP
                        ↓
                  prospectMapper.ts                 (cliente)
                        ↓
                  Prospect
                        ↓
                  deriveOpportunities()             (dominio)
```

**La frontera ya existe y está sana.** El adapter traduce `websiteUri → website`,
`nationalPhoneNumber → phone`, `userRatingCount → reviewCount`. El dominio nunca
ve un `Place` de Google. Esto es un `PlaceEvidenceMapper` sin nombre.

### 3.1 🔴 Hallazgo que gobierna todo el diseño

El adapter **destruye la distinción entre ausencia y cero**:

```ts
website: place.websiteUri || "",     // sin sitio  →  ""
rating:  place.rating || 0,          // sin nota   →  0   ← y 0 es una nota real
reviewCount: place.userRatingCount || 0,
```

Y el cliente intenta reconstruirla después con `textOrAbsent` / `numberOrAbsent`
(`prospectMapper.ts:55-87`). **La información ya se perdió río arriba.**

Un negocio sin calificación y uno calificado con 0 llegan idénticos. Es una
violación de **R-38** en el borde del sistema, anterior a este sprint.

**Por qué decide este diseño:** `photos?.length || 0` cometería exactamente el
mismo error, y precisamente sobre la distinción que el §5 del encargo exige
—Caso A «no tiene fotos» frente a Caso C «no lo sabemos»—. `PlaceEvidence` debe
nacer sin ese defecto.

### 3.2 🔴 El defecto ya está reconocido dentro del Opportunity Score

`opportunityScore.ts:251-261` no solo sufre la pérdida del §3.1: **la documenta y
la compensa deliberadamente**.

```ts
// R-38: rating 0 y reviewCount 0 se tratan como AUSENCIA de dato, no como
// reputación nula — el contrato no permite distinguirlos (desviación A-03).
{ name: "calificación",     value: input.rating > 0 ? … : null },
{ name: "número de reseñas", value: input.reviewCount > 0 ? … : null },
```

Es decir: **el Score sacrifica hoy la capacidad de puntuar un negocio realmente
calificado con 0**, porque el contrato no le permite distinguirlo de uno sin
calificar. Prefiere no medir antes que asumir — R-38 aplicado correctamente
sobre un contrato defectuoso.

> **Esto reencuadra H-14.F.** No es «añadir fotos»: es **dar al contrato la
> fidelidad que hoy le falta**. `photoCount` es el caso nuevo; `rating` y
> `reviewCount` son casos viejos que llevan tiempo degradados.

### 3.3 🟠 La cita de la desviación no concuerda

El comentario invoca **«desviación A-03»**, pero A-03 en `AR-05 §5.1` es:

> «`LeadRepository` no expresa la identidad (Referencia de Origen, Usuario) ni
> la Unidad de Registro atómica» — 🟡 `Partially Resolved`

**No guarda relación con reputación.** O el comentario cita un identificador
equivocado, o existe otro registro con numeración propia.

**No lo resuelvo aquí.** El estado de una desviación solo cambia en un sprint de
gobernanza, y AR-05 §5.1 es el registro vivo. Se reporta para que quien gobierne
verifique la trazabilidad.

### 3.4 Consumidores que hoy confunden 0 con ausencia

Auditados uno a uno. **Ninguno se parchea en este sprint.**

| Fichero | Línea | Expresión | Comportamiento |
|---|---|---|---|
| `LeadCard.tsx` | 90 | `(lead.rating ?? 0) > 0 \|\| …` | Un negocio calificado 0 se muestra «sin reputación» |
| `LeadCard.tsx` | 252, 257 | `lead.rating && lead.rating > 0` | Ídem |
| `OpportunityHero.tsx` | 44, 136, 139-140 | `(lead.rating ?? 0) > 0` | Ídem |
| `LeadLibrary.tsx` | 178-179 | `lead.rating > 0` | **Sin `??`** — asume no opcional |
| `opportunityScore.ts` | 254-255, 259 | `input.rating > 0` | Deliberado (§3.2) |
| `scoring.ts` | 1 | `calculateScore(rating: number, …)` | **Firma no admite `null`** |

**Migración necesaria en H-14.F.1:** ninguna, si `PlaceEvidence` se introduce
**sin alterar los campos actuales de `Prospect`**. Ver §11.

## 5. Modelo de `PlaceEvidence`

### 5.1 Estructura recomendada — plana y tri-estado

```ts
export type PlaceEvidenceVersion = "PE-1.0";

export interface PlaceEvidence {
  /** Qué señales se recogieron. Distingue «no tiene fotos» de
   *  «se recogió antes de que pidiéramos fotos». */
  version: PlaceEvidenceVersion;

  /** `null` = no observado. Cadena = sitio registrado. */
  websiteUrl: string | null;
  phone: string | null;

  /** `null` = no observado. `0` es un valor real, no una ausencia (R-45). */
  rating: number | null;
  reviewCount: number | null;
  photoCount: number | null;
}
```

### 5.2 Por qué plana y no anidada

La estructura sugerida en el encargo agrupaba (`website: { present }`,
`visualPresence: { photoCount }`). **Se descarta:**

- `{ present: boolean }` para un único booleano añade una indirección sin añadir
  significado, y **no puede expresar «no observado»** — justo el tercer estado
  que el Caso C necesita.
- La agrupación ya la comunica el nombre del campo.
- El proyecto prohíbe construir generalidad especulativa. Si un día `visual`
  crece, se anida entonces.

### 5.3 Por qué `null` y no `undefined`

`null` es **explícito**: obliga a decidir. `undefined` se confunde con «campo que
olvidé rellenar». Y encaja con la disciplina ya vigente en `Prospect.score`
—`typeof score === "number"`, nunca `!!score`— donde **`0` es un valor real**.

### 5.4 Lo que `PlaceEvidence` NO lleva

`photos[].name` (referencias de imagen) · `widthPx` / `heightPx` ·
`authorAttributions` · cualquier juicio de calidad · cualquier campo con
nomenclatura de Google.

### 5.4bis Criterios de admisibilidad por campo

> **Prueba: ¿puede AKVEZ explicar ante un jurado exactamente de dónde salió este
> dato?** Un campo que no la supere no entra.

| Campo | Fuente | Observado | `null` | `0` | Consumidores previstos |
|---|---|---|---|---|---|
| `version` | AKVEZ | — | ❌ obligatorio | — | Caso C de fotos |
| `websiteUrl` | `places.websiteUri` | ✅ directo | sin sitio registrado | n/a | `WEB_PRESENCE` · `OWNED_DOMAIN` · PV-1.0 |
| `phone` | `places.nationalPhoneNumber` | ✅ directo | sin teléfono registrado | n/a | Ninguno hoy — ver aviso |
| `rating` | `places.rating` | ✅ directo | no publicado | **calificación real de 0** | Reputación del Score |
| `reviewCount` | `places.userRatingCount` | ✅ directo | no disponible | **cero reseñas observadas** | Reputación del Score |
| `photoCount` | `places.photos.length` | ✅ derivado | recogido antes de `PE-1.0` | cero fotos observadas | `VISUAL_ASSETS` |

⚠️ **`phone` no tiene consumidor hoy.** H-14.D lo descartó como oportunidad —
«Places no lo registra» ≠ «el negocio no tiene». Se incluye porque **ya viaja en
el pipeline actual** y excluirlo perdería información existente, no porque se le
haya encontrado uso. Si en H-14.F.1 sigue sin consumidor, es legítimo dejarlo
fuera.

### 5.5 Dónde vive la regla de «plataforma de terceros»

`PlaceEvidence` transporta **la URL**. Qué hosts cuentan como plataforma de
terceros es una **regla**, y las reglas viven en `domain/`. La observación es la
cadena; la clasificación es criterio.

## 6. Mapper

```
GooglePlace  →  PlaceEvidenceMapper  →  PlaceEvidence
```

**Responsabilidad única: traducir y preservar.**

```
place.websiteUri          → websiteUrl   (ausente → null, nunca "")
place.nationalPhoneNumber → phone        (ausente → null)
place.rating              → rating       (ausente → null, nunca 0)
place.userRatingCount     → reviewCount  (ausente → null)
place.photos              → photoCount = photos.length; ausente → 0
```

⚠️ **La única asimetría, y es deliberada.** Google **omite `photos` cuando no
hay ninguna**. Como el `FieldMask` de `PE-1.0` sí lo pide, su ausencia en la
respuesta significa **cero fotografías observadas**, no «no observado».

`photoCount = null` queda reservado para un caso distinto: evidencia recogida
bajo una versión anterior que no pedía el campo. De ahí que `version` sea
obligatoria.

**El mapper no decide nada.** No sabe qué es una oportunidad, no clasifica hosts
y no juzga. Si alguien siente la tentación de escribir un `if` de negocio ahí,
está en el fichero equivocado.

## 7. FieldMask

```
+ places.photos
```

Un solo campo añadido. Nivel **Essentials**, y AKVEZ ya factura **Enterprise**:
**coste adicional cero** (H-14.E §10.1).

| Metadato | ¿Se usa? |
|---|:---:|
| `photos.length` | ✅ único dato necesario |
| `name` (referencia) | ❌ no se solicita el binario ni se guarda |
| `widthPx` · `heightPx` | ❌ resolución no es calidad |
| `authorAttributions` | ❌ prohibido por E-1 y no documentado |

La API no permite pedir subcampos de `photos` por separado: se recibe el objeto
completo. **La disciplina es de mapeo, no de petición** — el mapper descarta todo
salvo la longitud, y nada más cruza hacia el dominio.

## 8. Regla de evidencia visual

### 8.1 Los tres casos

| | Condición | ¿Oportunidad? | Confianza |
|---|---|:---:|---|
| **A** | `photoCount === 0` | ✅ **Sí** | alta |
| **B** | `photoCount > 0` | ❌ **No** | — |
| **C** | `photoCount === null` | ❌ **No** | — |

### 8.2 Caso A — la única que se emite

```
id        VISUAL_ASSETS
title     «Sin material visual en Google»
evidence  «Su ficha de Google Places no registra ninguna fotografía.»
offer     «Podrías contemplar el contenido visual dentro del alcance
           de la propuesta.»
rule      «photoCount === 0 en Google Places»
```

**`confidence` mide la certeza del hecho observado, no la del resultado
comercial.** Es alta porque el recuento es exacto. Confundir ambas cosas sería
volver a prometer resultados.

### 8.3 Caso B — por qué el silencio es correcto

Tener fotografías **no dice nada sobre su adecuación**. Cuarenta fotos de
clientes con el móvil no son un activo visual, y AKVEZ no puede distinguirlas de
cuarenta profesionales. Emitir aquí cualquier oportunidad exigiría un juicio de
calidad que no tenemos. **No se emite nada.**

### 8.4 Caso C — ausencia declarada

Evidencia recogida antes de `PE-1.0`. No se emite oportunidad. La interfaz
**puede** declarar «no evaluado» conforme a R-38, pero nunca inferir cero.

### 8.5 Afirmaciones prohibidas

> «Necesita fotografía profesional» · «Sus fotos son malas» · «Necesita un
> fotógrafo» · «Su presencia visual es deficiente» · «Pierde clientes por no
> tener fotos» · «Sus imágenes son de baja calidad»

Y una menos evidente pero igual de falsa:

> ❌ **«El negocio no tiene fotografías.»**

AKVEZ solo puede afirmar que **su ficha de Google** no las tiene. El negocio
puede tener un Instagram excelente. La distinción debe sobrevivir al copy final.

## 9. Frontera con Service Fit

```
PlaceEvidence  →  Opportunity  →  Service Fit  →  Professional Services   ✅

PlaceEvidence  →  Photography recommendation                              ❌
```

**La evidencia declara qué se observó. Service Fit decidirá qué servicios encajan
—si el PO aprueba antes APS-01 F1/F2 (H-14.D)—.**

`VISUAL_ASSETS` es una señal sobre el **activo**, no sobre el **servicio**. Que
la resuelva un fotógrafo, un diseñador con banco de imágenes o el propio dueño
con su móvil es una decisión del profesional, no de AKVEZ.

Esto preserva E-5: se amplía la evidencia sin construir infraestructura de F2.

## 9bis. Compatibilidad hacia atrás

### 9bis.1 La decisión que evita toda regresión

> **`PlaceEvidence` se introduce *junto a* los campos actuales de `Prospect`, no
> en su lugar.**

`Prospect.rating` y `Prospect.reviewCount` **conservan su tipo y su semántica
actuales**. Los seis consumidores del §3.4 siguen funcionando exactamente igual,
y `calculateScore` mantiene su firma `(rating: number, …)`.

`PlaceEvidence` es un **canal nuevo y paralelo**, consumido por
`deriveOpportunities`, que hoy solo necesita `websiteUrl` y `photoCount` — dos
campos sin ningún consumidor que confunda 0 con ausencia.

### 9bis.2 Coste de esta decisión

**Duplicación temporal.** `rating` viajará por dos caminos con fidelidad
distinta: degradado en `Prospect`, fiel en `PlaceEvidence`. Es deuda consciente
y acotada.

La alternativa —migrar los seis consumidores y la firma de `calculateScore` en
el mismo sprint— **cambiaría el Score de negocios reales** (uno calificado con 0
pasaría de «no medido» a «medido en 0»), y eso toca WP-01. **No es una decisión
de ingeniería.**

### 9bis.3 Migración futura, fuera de alcance

Cerrar la duplicación exige, en este orden: `calculateScore` acepta `null` →
migrar los seis consumidores → retirar los campos degradados de `Prospect` →
**decisión de gobernanza** sobre el cambio de Score. Sprint propio.

## 9ter. Versionado

```ts
type PlaceEvidenceVersion = "PE-1.0";
```

**Qué versiona:** el **conjunto de señales recogidas**, no su formato ni su
significado.

| Cambio | ¿Nueva versión? |
|---|:---:|
| Se añade una señal nueva al `FieldMask` | ✅ **Sí** |
| Se deja de recoger una señal | ✅ **Sí** |
| Cambia el significado de `null` o `0` en un campo | ✅ **Sí** |
| Renombrar un campo, reordenar, ajustar comentarios | ❌ No |
| Cambia una regla de derivación | ❌ No — la regla no es evidencia |

**Por qué es obligatoria y no opcional.** Es lo único que distingue *«observamos
cero fotografías»* de *«recogimos esta evidencia antes de mirar fotografías»*.
Sin ella, el Caso C del §8 es indistinguible del Caso A, y toda la disciplina de
este diseño se derrumba en el primer lead antiguo.

Precedente en el proyecto: `Prospect.scoreVersion` y el `valueModelVersion` de
PV-1.0 (H-14.C) resuelven el mismo problema para el Score y el valor.

## 10. Opportunity Score

**De acuerdo con la recomendación: no modificarlo.** Ni categoría nueva, ni
alimentar una existente.

Tres razones:

1. **Gobernanza.** Los pesos son WP-01 y los gobierna ADR-14. Añadir una señal
   exigiría ese trámite y redistribuir el 100 %.
2. **Semántica.** El Score mide *potencial comercial del lead*. Que su ficha no
   tenga fotos no lo hace mejor ni peor cliente.
3. **Precedente ya establecido.** PV-1.0 (H-14.C) quedó explícitamente fuera del
   Score por el mismo motivo. La evidencia visual sigue la misma vía.

## 18ter. 🔴 H-14.F.1 — BLOQUEADO · el diseño tiene un hueco

**Estado: implementación detenida. Cero líneas de código modificadas.**

### El error está en este documento, no en el encargo

§17 planificó cuatro pasos de transporte y estimó «pequeño-mediano»:

> «4. Transporte por el DTO y reconstrucción en `prospectMapper`»

**No audité la cadena de transporte.** Asumí que la salida del adapter llegaba
más o menos directa al DTO. Es falso. La cadena real es:

```
googlePlacesAdapter.ts        infrastructure   ← FieldMask
prospectDiscoveryPort.ts      🔴 DOMINIO — puerto
discoverProspects.ts          application
Lead.ts                       🔴 DOMINIO — entidad
leadMapper.ts                 🔴 PERSISTENCIA
inMemoryLeadAdapter.ts        🔴 PERSISTENCIA
leadResponseMapper.ts         contrato
prospectSearch.ts             contrato público
prospectMapper.ts             cliente
Prospect                      cliente
```

**Nueve ficheros, dos de ellos de dominio y dos de persistencia.**

### Por qué esto bloquea

1. **§12 del encargo lo prohíbe expresamente:** «Si para implementar
   `PlaceEvidence` necesitas modificar … arquitectura de persistencia … no lo
   hagas.» `photoCount` **debe sobrevivir a la persistencia** para llegar al DTO,
   porque el DTO se construye desde el Lead persistido.

2. **Contradice el propio §4 de este diseño.** `PlaceEvidence` se concibió como
   capa separada, agnóstica del proveedor. Enhebrar `photoCount` a través de
   `Lead` —una entidad de dominio que representa *un negocio*, no *lo que
   observamos de él*— es exactamente la contaminación que el diseño quería
   evitar. Quedarían dos representaciones de evidencia compitiendo.

3. **No existe canal de evidencia.** Hoy la evidencia viaja **dentro** de la
   entidad de dominio. `PlaceEvidence` no puede «insertarse»: habría que crear
   el canal, y eso es un sprint, no un paso.

### Alternativas

| # | Alternativa | Coste | Riesgo |
|---|---|:---:|:---:|
| **A** | Enhebrar `photoCount` por los nueve ficheros | medio | 🔴 contamina dominio y persistencia · prohibido por §12 |
| **B** | Canal de evidencia paralelo a `Lead`, persistido aparte | alto | 🟠 correcto, pero es rediseño de persistencia |
| **C** | **No persistir.** Correlacionar en la ruta los candidatos (que traen `photoCount`) con los Leads persistidos, por `sourceDesignation` | **bajo** | 🟡 la evidencia **no sobrevive**: la Biblioteca vería `photoCount: null` siempre |
| **D** | Detener H-14.F.1 y decidir antes | cero | 🟢 |

**Sobre C** —la única barata—: el `prospectSearchRoute` ya dispone de
`deduplicatedLeads` **y** de `leads` en el mismo ámbito, así que la correlación
es posible sin tocar dominio ni persistencia. Y `photoCount: null` para un Lead
recargado **es semánticamente correcto** según §8.4: no se observó bajo `PE-1.0`.

Pero significa que la evidencia **solo existe durante la ejecución que la
descubrió**. Si eso es aceptable o no es una decisión de producto, no de
ingeniería: no la tomo.

### Qué documento debería actualizarse

Ninguno del Blueprint. **Este documento** es el que estaba incompleto: §17 debe
reescribirse tras decidir entre B, C y D.

### Decisión que requiere Product

> **F-6 — ¿La evidencia observada debe persistir con el Lead, o basta con que
> exista durante la ejecución que la descubrió?**

De la respuesta depende todo: **sí** → alternativa B, sprint de persistencia;
**no** → alternativa C, implementable de inmediato.
