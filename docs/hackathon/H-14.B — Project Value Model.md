# H-14.B — Project Value Model

**Sprint:** H-14.B · Diseño del modelo de valor potencial
**Estado:** ✅ Diseño completado · **cero código modificado**
**Base:** H-14.A′ (`bf22c72`)
**Fecha:** 2026-08-07

---

## 1. Objetivo

Diseñar el modelo que permitirá mostrar un **rango de valor potencial del
proyecto** en la tarjeta de una oportunidad, de forma determinista, explicable y
versionable. **No se implementa nada.**

---

## 2. Contexto

APS-04 §10.3 ya contempla la presentación —«rango de valor potencial del
proyecto (`USD 800 – 1,500`)»— y le asigna el color de éxito. **Define cómo se
muestra; no define cómo se calcula.** Ese hueco es lo que este documento cubre.

El ejemplo `800 – 1,500` de APS-04 es **ilustrativo del tratamiento visual**, no
un valor universal. No debe llegar al código como constante.

---

## 3. Problema

El modelo debe poder responder, ante el usuario:

> «¿Por qué este lead tiene un rango de USD X – Y?»

Cualquier modelo cuya única respuesta sea «lo calculó la IA» queda descartado por
construcción. La explicación debe caber en una frase que un profesional pueda
repetirle a un cliente sin mentir.

### 4.1 Datos insuficientes — declarado explícitamente

**AKVEZ no tiene ningún anclaje con dinero real.** No conoce tarifas de mercado,
ni lo que el usuario cobra, ni presupuestos de los negocios, ni un solo proyecto
cerrado. Toda cifra base será, inevitablemente, **un parámetro de producto
decidido por el PO**, no un valor derivable.

Esto no bloquea el diseño —el sprint lo prevé— pero define el límite honesto del
modelo: **AKVEZ puede estructurar la estimación; no puede originar sus números.**

## 6. Modelos candidatos

### Modelo A — Rango base por tipo de oportunidad

**Fórmula conceptual**

```
rango = Σ rangoBase(tipo)   para cada oportunidad derivada
```

**Inputs:** `EvidenceBasedOpportunity[]`
**Output:** `{ min, max, currency, modelVersion }`

**Ejemplo.** Un negocio sin sitio web produce `WEB_PRESENCE`. Su rango base
—**parámetro pendiente `PV-01`**— determina la salida directamente.

- ✅ Cada input ya está respaldado por evidencia. No introduce ninguna variable nueva.
- ✅ Explicación de una frase: «tiene una oportunidad de presencia web, cuyo rango base es X–Y».
- ✅ Dos parámetros en total. Testeable de forma exhaustiva.
- ❌ Granularidad baja: hoy solo hay dos tipos, luego solo dos resultados posibles.
- ❌ No distingue una panadería de barrio de un restaurante de cuarenta mesas.

### Modelo B — Alcance acumulado

**Fórmula conceptual**

```
rango = base + Σ componentes + (complejidad × multiplicador)
```

- ✅ Extensible: cada capacidad futura entra como componente.
- 🔴 **`complejidad` no tiene fuente de datos.** AKVEZ no inspecciona sitios, no
  cuenta páginas, no conoce alcance. Habría que inventarla o pedírsela a Gemini
  —que tampoco la puede observar—.
- 🔴 El multiplicador produce cifras de aspecto preciso a partir de una variable
  fabricada: es **falsa precisión con estructura matemática**, la forma más
  peligrosa de todas.

**Descartado.** Falla la regla de evidencia en su input central.

### Modelo C — Híbrido: tipo × señal de escala del negocio

**Fórmula conceptual**

```
rango = rangoBase(tipo) × factorEscala(reviewCount)
```

- ✅ `reviewCount` es un dato duro observado.
- ✅ Intuitivamente cierto: un negocio con 800 reseñas suele ser mayor que uno con 5.
- 🔴 Exige umbrales arbitrarios («¿a partir de cuántas reseñas sube el factor?»).
- 🔴 Afirma implícitamente que **reseñas ⇒ presupuesto**, relación que AKVEZ no
  puede demostrar y que es falsa en muchos casos (un negocio popular y precario
  existe perfectamente).
- 🔴 Convierte una medida de reputación en una medida de dinero. Es el mismo
  error conceptual que el §12 prohíbe con el Score, aplicado a otra variable.

**Descartado para v1.** Reevaluable si algún día existen datos de proyectos
cerrados que confirmen o refuten la relación.

### Modelo D — Rango declarado por el profesional *(propuesta propia)*

**Fórmula conceptual**

```
rango = rangoDeclaradoPorElUsuario(tipo de proyecto)
```

El profesional declara una vez lo que suele cobrar por un sitio nuevo y por un
rediseño. AKVEZ aplica **sus propios números** a la oportunidad detectada.

- ✅ **Elimina de raíz el problema de origen:** AKVEZ nunca afirma conocer
  precios de mercado. Presenta los del usuario.
- ✅ Explicación perfecta: «tu rango para un sitio nuevo es X–Y».
- ✅ Resuelve lo que el propio sprint señala: *«no asumas que todos los
  profesionales cobran lo mismo»*.
- ✅ Determinista, versionable y trivial de testear.
- ❌ **Requiere un campo de perfil que hoy no existe.**
- ❌ Vacío hasta que el usuario lo rellene → estado «sin información suficiente».
- ❌ Añade fricción al alta, que H-11 acaba de aligerar deliberadamente.

## 8. Modelo recomendado

> **Modelo A como v1, con la arquitectura preparada para que el Modelo D lo
> sustituya sin romper nada.**

**Por qué A y no D directamente:** D es superior conceptualmente, pero depende de
un campo de perfil inexistente y de añadir fricción a un alta que H-11 acaba de
reducir a la mitad. A se puede implementar hoy sin tocar el perfil.

**Por qué A y no B ni C:** son los únicos dos que introducen variables que AKVEZ
no puede sostener. Seis sprints eliminando afirmaciones no demostrables se
perderían al reintroducirlas dentro de una fórmula.

**La transición es limpia** porque ambos comparten firma: dado un conjunto de
oportunidades, devuelven un rango. La diferencia es de dónde salen los números
—parámetro de producto en A, perfil del usuario en D—, no de estructura.

### 8.1 Fórmula conceptual

```
entrada:  EvidenceBasedOpportunity[]
salida:   { min, max, currency, modelVersion, basis } | null

si oportunidades está vacío        → null   (no se muestra nada)
si no:
    min = Σ rangoBase(op.id).min
    max = Σ rangoBase(op.id).max
    basis = lista de los tipos que contribuyeron
```

`basis` existe por la misma razón que `evidence` en H-14.A′: **la salida debe
poder explicarse sin leer el código.**

### 9.1 Prueba de admisibilidad de APS-17 §3

APS-17 somete todo parámetro a esta prueba:

> «Si este valor se duplicase, se redujese a la mitad o desapareciese, ¿tendría
> el usuario un conjunto de Leads distinto en su Biblioteca?»

**Aplicada a `PV-01`…`PV-03`: NO.** El conjunto de Leads lo determinan la
búsqueda, la deduplicación y el registro. Un rango de valor **no filtra, no
ordena y no descarta nada**. → **Admisibles.**

⚠️ **Esta admisibilidad es condicional.** Si el rango llegara alguna vez a
ordenar o filtrar Leads, pasaría a ser regla de dominio disfrazada de
configuración y **dejaría de ser admisible**. De ahí la restricción de §12: el
valor es estrictamente presentacional.

## 10. Manejo de la incertidumbre

**La amplitud del rango es el mensaje.** Un rango estrecho comunica una precisión
que no tenemos; uno amplio comunica honestamente que es orientativo.

| Elemento | Decisión |
|---|---|
| Formato | Siempre rango. **Nunca un valor único.** |
| Etiqueta | «Rango orientativo» — literal de APS-04 |
| Explicación | «Estimación orientativa basada en el tipo de oportunidad detectada.» |
| Nivel de confianza | **No en v1.** Un porcentaje de confianza sería otra cifra sin respaldo |
| Origen | `basis` disponible para la interfaz |

### Lenguaje prohibido

Nunca: «este negocio gastará» · «puedes cobrar» · «el proyecto vale» · «ganará» ·
«presupuesto» · «cotización». Siempre: «valor estimado del proyecto» / «rango
orientativo».

---

## 11. Casos límite

| Caso | Comportamiento |
|---|---|
| Sin oportunidades derivadas | **No se muestra nada.** Ni rango, ni cero, ni «desde» |
| Una oportunidad | Rango de su tipo |
| Varias oportunidades | Suma de rangos |
| Tipo sin parámetro configurado | **No se muestra.** Nunca un valor por defecto |
| Lead antiguo sin estimación | Se declara la ausencia (R-38) |

**Regla rectora:** ante la duda, no se muestra. *Sin información suficiente* es
una respuesta legítima y preferible a un rango inventado.

## 12. Relación con el Opportunity Score

**Son magnitudes distintas y no deben derivarse una de otra.**

| | Opportunity Score | Valor potencial |
|---|---|---|
| Mide | Potencial comercial **para este usuario** | Alcance económico del proyecto |
| Escala | 0–100 | Moneda |
| Gobierno | APS-08 · WP-01 · ADR-14 | APS-17 (propuesto) |
| Efecto | **Ordena** los Leads | **No ordena nada** |

Un Score de 90 significa «vale la pena contactarlo», no «pagará más». Una
panadería sin web puede puntuar 91 y ser un proyecto pequeño.

🔴 **Restricción arquitectónica:** el valor potencial **no puede alimentar el
Score ni el orden de los Leads**. Si lo hiciera, dejaría de pasar la prueba de
APS-17 §3 y tocaría WP-01, que gobierna ADR-14.

## 13. Relación con el Professional Profile

Hoy `skills` es texto libre. El modelo v1 **no lo usa y no lo modifica**.

El Modelo D depende de un campo que no existe: los rangos que el profesional

la respuesta correcta a la observación del sprint de que no todos cobran lo
mismo: en lugar de que AKVEZ suponga tarifas, se las pregunta una vez.

Dependencia declarada, sin diseño de campo ni de contrato en este sprint.

## 14. Versionado

**Precedente reutilizable:** `Prospect.scoreVersion` ya existe y resuelve
exactamente este problema para el Score.

```
valueModelVersion: "PV-1.0"
```

Se persiste **junto a la estimación**, no se recalcula al leer. Consecuencia:

```
Lead calculado con PV-1.0  →  conserva PV-1.0 y su rango
Lead nuevo con PV-2.0      →  usa PV-2.0
```

Un cambio de parámetros en APS-17 **no reescribe el pasado**, igual que un cambio
de WP-01 no reescribe Scores ya calculados. La interfaz puede declarar la versión
cuando difiera de la vigente.
